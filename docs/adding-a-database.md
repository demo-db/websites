# Adding a database

1. Create or update a provider repository with a source fixture and reproducible provenance, a `manifest.json`, `metadata/contract.json`, `metadata/checksums.json`, and the exports and model/meaning files named by the provider contract. Generate `ovdb-database.json` from the validated publisher descriptor and schema projection; include its checksum. Validate it against the byte-pinned `ovdb-database/draft-1` schema published by the website. The current provider adapter uses SQLite fixtures and publishes SQLite, SQL, CSV, and JSON exports. The website rendering contract describes databases, recordsets, fields, relationships, exports, and capabilities independently of any storage engine; a future provider adapter may build the same contract from another engine without adding engine- or database-specific rendering branches. Preserve the source schema and names; do not prepare a second hand-edited schema for the website. Add OVDB publication metadata and declare table concepts only where the provider’s meaning metadata supports them.
2. Validate and publish the provider repository. Add one entry to `config/databases.json` with its stable ID, repository URL, full immutable main commit, and SHA-256 of that commit’s `metadata/contract.json`. Rebuild locally from a checkout override, inspect all routes and downloads, and run the website checks.
3. Declare the dataset in `config/format-matrix.json`: for each format, either `download` with its origin (`provider`, `provider-artifact`, `derived`, `archive`, `provider-script`) or `unavailable` or `planned` with a specific reason, and its initial state under `baseline`. JSON, YAML and PostgreSQL scripts are generated from the pinned fixture; the MySQL script (origin `provider-script`) is written by DataTug into the provider repository's `dialect-scripts/` (`node scripts/dialect-scripts.mjs generate --provider <checkout> --tools <dir>`, see [dialect-scripts.md](dialect-scripts.md)); the inGitDB archive packs the `ingitdb/` directory at the revision named in `ingitdbRevisions`. Run `DEMODB_UPDATE_DERIVED_LOCK=1 node scripts/prepare-databases.mjs` to pin what was generated, review the lock diff, and regenerate `docs/format-matrix.md` with `node scripts/format-matrix-doc.mjs --write`. The build and `scripts/test-format-matrix.mjs` fail when the declaration, the metadata and the produced files disagree. See [format-matrix.md](format-matrix.md).
4. The build creates the host bundle and `scripts/deploy-hosts.mjs` creates its Cloudflare Pages project `demodb-<id>` and moves `<id>.demodb.dev` onto it on the next deploy from `main`. Confirm its `siteHost` equals `<id>.demodb.dev`, then merge through the normal CI deploy. The Worker resolver and static pages derive the database from the registry.

For example, adding Sakila would mean a `demo-db/sakila` provider, a pinned `sakila` registry entry, and `sakila.demodb.dev` in the Worker custom-domain list. The catalogue card, database landing page, tables, schema, downloads, queries, about page, model page, similarity ranking, CORS, discovery, and OVDB redirects use the same components and host mapping; no Sakila-specific UI code is added.

Provider table names, exports, model entity aliases, row counts, views, and capabilities come from each provider’s contract and manifest. The provider publisher validates the manifest’s table/entity mapping before website builds consume it. A missing pinned export or checksum fails the build instead of quietly producing a partial site.
